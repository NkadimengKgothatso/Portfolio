CareQueue

Clinic appointment and virtual-queue platform with machine-learning wait-time prediction.

  • JavaScript
  • Firebase Auth
  • Firestore
  • PWA
  • Python
  • Flask
  • scikit-learn
  • pandas
  • Jest
  • GitHub Actions
  • Codecov
Live demo Source

Problem

Patients at South African public clinics often wait for hours with no idea of their queue position or how long they'll be waiting.

My contributions

  • Built the wait-time prediction pipeline end to end: Firestore export, cleaning and outlier removal, feature engineering, model training, and a Flask /predict API deployed on Render that the patient dashboard calls.
  • Replaced the first Random Forest model with a Gradient Boosting Regressor on engineered features, evaluated with 5-fold cross-validation and mean absolute error.
  • Built the patient dashboard (live queue position, status and estimated wait), with a rule-based fallback estimate when the prediction service can't be reached.
  • Set up the GitHub Actions test workflow with Codecov coverage reporting, and wrote Scrum and architecture documentation (sprint backlogs, burndown charts, retrospectives, 4+1 views).
Solution & technical challenges

Solution

A Progressive Web App with three roles. Patients book appointments, join virtual queues and track their position. Staff manage queues, walk-ins and availability. Admins manage clinics and staff and view analytics. Authentication uses Firebase Auth (including Google sign-in), and data lives in Firestore.

Challenges

  • Very little real history to learn from. I wrote scripts to log and backfill queue history (plus synthetic data) so the model had enough to train on.
  • Overfitting on a small dataset. The training script compares train and test MAE and warns when the gap gets too large.
  • An unreliable network dependency. The dashboard falls back to a formula-based estimate instead of showing nothing.
CTO · Private company Live 2026

Beko ComplianceOS

Compliance platform that helps South African SMEs track their SARS, CIPC and other regulatory obligations.

  • JavaScript (ES modules)
  • Supabase Auth
  • PostgreSQL
  • Row-Level Security
  • Supabase Storage
  • SQL
  • PWA
  • Vercel
Live site

Source code is private company IP. Happy to walk through the architecture in an interview.

Problem

Small businesses and sole proprietors often don't know which regulatory obligations apply to them or when they're due. The answer depends on their structure, size, VAT status, staff and industry.

My contributions

  • As CTO of a private company I lead all technology decisions, and I built the platform myself from first commit to production on a custom domain.
  • Designed a PostgreSQL schema of 12 tables with row-level security policies, so each user can only ever read or write their own data and documents.
  • Implemented authentication flows: email and password, 8-digit email verification codes, Google sign-in, password reset and route guards (verify, then onboard, then dashboard).
  • Built a rules-based obligation engine. Onboarding answers generate a personalised set of obligations and a 0–100 compliance score, and obligations that don't apply are excluded from the score instead of counted as zero.
Solution & technical challenges

Solution

An installable PWA with a multi-step onboarding wizard and a dashboard of deadlines and alerts. It also has a documents centre (validated per-user uploads), tender alerts, a FICA-style AML risk screener, consultation booking with partner law firms, and an admin panel.

Challenges

  • Changing the data model mid-project. I migrated the backend from Firebase/Firestore (documents) to Supabase/PostgreSQL (relational), using idempotent SQL migration scripts that can safely be re-run.
  • Keeping scoring explainable. Every obligation carries an explicit applicability rule, and the model is documented for review by legal professionals.
  • Security as a design constraint. Access control is enforced in the database (RLS), not just hidden in the UI.
Academic · Team of 6 Live 2026

Wits Quest

Location-gated campus game: walk to real Wits landmarks, answer trivia, collect cards and battle other students.

  • TypeScript
  • React
  • Vite
  • Node.js
  • Express
  • Supabase
  • PostgreSQL
  • Vitest
  • MkDocs
Live app Documentation

Source code is hosted on the university's Gitea instance and isn't public. The docs site I maintain is on GitHub.

Problem

Static campus tours don't hold students' attention. A game that rewards physically visiting places has a core integrity problem: the location a phone reports can't be trusted.

My contributions

  • Built authentication in Sprint 1: login and registration UI, the React auth context, and server-side credential checks.
  • Owned achievements: admin-defined rules (cards collected, battles won, streaks, trails completed) checked server-side after every answer and match, with an in-game unlock pop-up.
  • Owned analytics and daily streaks, including per-question pass rates that power the curators' "needs repair" flag for questions almost everyone gets wrong.
  • Co-led documentation (15% of the milestone mark): API reference and endpoint catalogue, database, testing and methodology. I built and deployed the MkDocs site and kept the stand-up notes.
Solution & technical challenges

Solution

A React + TypeScript frontend with an Express API on Supabase (PostgreSQL, Auth, Realtime). The server decides everything that matters: location check-ins, trivia marking, battle outcomes and rewards. Each of the six members owned one domain end to end.

Challenges

  • Never trusting the client. Location and battle logic moved server-side, with anti-cheat checks for walking time and duplicate answers, plus trading rules that prevent card funnelling.
  • Six people, one codebase. We used a branch per task and reviewed PRs citing bug-tracker IDs. CI enforced lint, type checks and a test-coverage gate raised from 60% to 80%.
  • Cross-member dependencies. My per-question pass rates were a hand-off another member's curation feature depended on, so they had to land early and stay stable.

The Silent Horn

3D browser game in three acts (run, drive, fight) through a jungle to an ancient shrine, built with Three.js for Computer Graphics & Visualisation.

  • JavaScript
  • Three.js
  • GLSL shaders
  • WebGL
  • Vite
  • Web Audio
Play the game Trailer Devlog Source

Problem

Build a complete, playable 3D game that runs in the browser: real-time rendering, physics-like vehicle handling and enemy AI, smooth at interactive frame rates, with a team of developers working on separate levels of one codebase.

My contributions: Level 2, "The River Road"

  • Owned the driving level end to end: a car chase along a jungle river road that ends going over a waterfall.
  • Built the vehicle controller (acceleration, steering, handbrake, solid collisions) and traffic of cars, vans, buses and wildlife crossing the road.
  • Designed the pursuer's AI as a finite-state machine with telegraphed attack moves (slam, PIT, shunt, pin, brake-check, ram, tyre shots, spike strips and kamikaze drones), tuned so every hit can be dodged.
  • Wrote a car-paint shader that hooks into Three.js materials with onBeforeCompile: it converts texels to HSV and repaints only the body, leaving glass, tyres, chrome and lights untouched.
Technical details
  • Fair AI, not a cheating one. Each attack is telegraphed with headlight strobes and lane lunges, and the pursuer weaves through traffic using the same rules as the player instead of passing through it.
  • Atmosphere on a frame budget. Dusk lighting, a rain shower, working car lights and a river gorge before the falls, while keeping frame timing steady.
  • Sound without audio files. Engine and effects synthesised in the browser with the Web Audio API.
  • Player choice. A car picker with distinct car stats and paint options, built on the paint shader.
Academic · Individual 2026

RAT: Repo Analysis Tool

Dashboard that measures how a Git repository evolved: churn, growth and code ownership per file, directory and author.

  • Node.js
  • Express
  • JavaScript
  • ECharts
  • Git internals
Source

Problem

Questions like "who owns this code?" and "where does change concentrate?" need exact metrics computed across tens of thousands of commits, and the answers need to come back fast.

Implementation

  • One streaming git log --numstat pass per repository (never a process per commit), parsing NUL-delimited output on the fly.
  • In-memory model with sparse per-file arrays, directory totals aggregated at parse time, binary-search range queries and a small FIFO cache.
  • REST API plus a dashboard with timelines, a treemap, hotspots, ownership charts, author merging (.mailmap) and zip-upload or URL-clone ingestion.
Validation & performance
  • Correctness: matched reference metric CSVs exactly for cJSON, redis and git.git (63,298 rows checked on git), plus 111 hand-computed fixture assertions.
  • Performance: parses php-src (118,756 commits) and then serves dashboard queries from memory in about 300 ms. Parse time is about 20% above git's own git log.
  • Edge cases: renames (-M50%), binary files and merge commits handled exactly as the specification defines.
